## xFrontier Bidirectional Feedback Findings
- Phase 18 must preserve three different authorities: the Frontier Isles ledger is local research truth, the feedback outbox is delivery intent, and the xFrontier finding/proposal ledger is upstream review state. None may be silently treated as another.
- The existing night-digest webhook is fire-and-forget with one retry and no durable cursor or receipt, so it is unsuitable as the transport foundation for cross-project feedback.
- The existing Scout MCP client demonstrates the correct process boundary—stdio MCP plus injectable test doubles—but it is scoped to the Frontier Isles server and cannot serve as an xFrontier feedback receipt store.
- A slug is not a stable cross-project id. Feedback envelopes must carry explicit xFrontier record ids or structure proposal ids plus the local ledger/ref evidence that produced the intent.
- Live MCP inspection on 2026-08-13 confirms three upstream write operations, not two: `report_finding`, `propose_annotation`, and `propose_structure_link`. The shared server description still says “two propose_* tools write,” so bridge safety must use an explicit allowlist rather than prose or `readOnlyHint` alone.
- None of the three write inputs exposes a caller-provided idempotency key. Frontier Isles therefore cannot safely infer retry deduplication from the transport; it must persist attempts and reconcile a returned remote id before retrying an ambiguous outcome.
- `list_proposals` is cursor-paged and exposes `pending|accepted|rejected`, full decision history, human-review provenance, conflicts, and dataset version. It currently returns zero items, so decision normalization needs fixtures rather than invented live examples.
- `list_findings` exposes stable finding ids, dataset-version staleness, and filer provenance but no cursor. Current live state remains 10 findings, all non-stale; only one has the newer `filed_by` field recorded.
- The current MCP proposal response explicitly states that only a person running the upstream CLI can accept or reject; this bridge must ingest those decisions, never manufacture them.
- Upstream proposal ids and decision ids are random eight-character handles, not content-derived ids. Every decision carries `proposal_id`, `accepted|rejected`, rationale, reviewer label/type, dataset version, and timestamp; reversals append another decision and the latest one determines status.
- Upstream human review can reverse an earlier decision and preserves the full history. Local ingestion must key individual decision receipts by remote decision id and recompute the latest status from ordered history instead of overwriting a single status cell as the sole evidence.
- The upstream review CLI warns explicitly that accepting a proposal does not modify `audit/`. The local inbox therefore needs a separate local disposition (`unreviewed|acknowledged|applied|released`) rather than aliasing the remote status.
- Frontier Isles `openDb()` uses one idempotent SQL migration string on every open with WAL enabled. New feedback tables can follow this pattern without versioned migration files, but table constraints and indexes must encode the state machine because existing databases upgrade in place.
- `apps/server` already owns both `better-sqlite3` and the MCP SDK, so the durable bridge can remain server-side without adding a second database client or transport dependency. The reusable envelope/normalizer should stay in a pure explicit `@frontier-isles/data/xfrontier-feedback` subpath.
- Live tool annotations mark all three xFrontier feedback writes `idempotentHint=false`; this confirms that a call timeout is an uncertain outcome, not a retry signal.
- The `list_proposals` cursor binds its filters and dataset version but not a ledger revision. Paging during concurrent upstream review is therefore not a snapshot read; ingestion must be idempotent by remote ids and tolerate duplicate/moved rows rather than treating a page count as a transaction.
- A finding has no resolved/decision lifecycle. Its `stale` flag only says the corpus dataset moved, so local review disposition must not manufacture an upstream resolution state.
- The implemented shared lower layer is `@frontier-isles/data/xfrontier-feedback`: a strict `xfrontier-feedback-envelope/v1` must cite an existing local ledger event/ref hash, and maps to inert tool intent data only. It cannot execute MCP calls.
- The server now owns a durable SQLite outbox with immutable envelopes, begun-call attempts, terminal/lease-expired receipts, proposal decision history, and finding/review inbox projections. These are exchange records, not a second research ledger.
- Delivery is deliberately singular and explicit: the CLI requires an exact pending outbox id plus `--confirm-non-idempotent-write`. Default `inspect`, `enqueue`, and `recover-expired` construct no MCP client; `pull` authorizes only the reviewed read tools.
- Read preflight is fail-closed on server `0.5.0` and explicit `readOnlyHint=true`, `destructiveHint=false`, `idempotentHint=true` for `stats`, `list_findings`, and `list_proposals`. Two complete equal sweeps provide a quiet-window observation without pretending the offset cursor is transactional.
- A write acknowledgement is trusted only when root/nested dataset versions and every echoed finding/proposal field match the immutable intent. Decision pull then rebinds the proposal again to the local envelope and exactly one success receipt, preventing short-id collision from importing another proposal's review.
- Once a delivery lease exists, every failure remains non-retryable uncertainty—even when the upstream ACK arrived but SQLite could not record success, or no terminal uncertainty receipt could be written. Expired leases require the explicit local-only `recover-expired` command and append a `lease_expired` receipt.
- `uncertain` cannot be cancelled or leased again. Successful remote ids are namespaced and transactionally single-owner across SQLite connections; legacy collisions still fail lookup rather than choosing an arbitrary outbox item.
- Remote acceptance and local use remain orthogonal. Local disposition advances `unreviewed → acknowledged → applied → released`; a later upstream rejection preserves applied/released as historical fact and exposes `needsReconciliation=true` until the remote state is accepted again.
- The final live read-only pull observed dataset `xf-6eb361265784`, 10 non-stale findings, zero proposals/conflicts/decisions, and `appliedAutomatically=false`. It used a disposable SQLite database; the real Frontier Isles database and xFrontier worktree were unchanged.
- xFrontier can make this safer upstream by accepting a unique `client_event_id`, checking expected dataset/content hash atomically, exposing immutable ledger-revision cursors and exact ID lookup, using atomic fsync/rename persistence, strengthening IDs, and adding finding/consumer acknowledgement lifecycles.

### Phase 19 protocol freeze (2026-08-13)

- A safe replay must resolve an existing `client_event_id` before re-evaluating current dataset or record preconditions. Otherwise an acknowledgement lost after a successful write becomes unrecoverable as soon as the corpus advances.
- The atomic claim key must be global to `client_event_id`, not scoped to a tool. A deterministic final filename derived only from the caller event ID lets `flag: 'wx'` arbitrate concurrent processes and prevents the same event ID from producing one finding and one proposal.
- A replay is valid only when the stored canonical request hash exactly matches the newly normalized request, including tool name and supplied preconditions. Reusing the same event ID for a different request is a hard conflict.
- A committed ledger record must be crash-durable before its acknowledgement is returned: write an exclusive same-directory temporary file, fsync it, atomically rename to the deterministic final path, then fsync the directory. Temporary files must not use the `.json` suffix so readers and validators ignore an interrupted write.
- Existing transport acceptance already asserts exactly three writers (`report_finding`, `propose_annotation`, `propose_structure_link`). The initialization prose is the stale surface: it still describes only the two proposal tools as writers.
- xFrontier already atomically publishes its MCP bundle as `server.next.mjs` then `renameSync(..., server.mjs)`, but that protects only executable replacement. Ledger records still need their own temp-file/fsync/rename/directory-fsync durability path.
- The built server bakes both dataset version and default ledger path; `XF_LEDGER_DIR` remains the required isolation override for every write-path test, while a rebuilt bundle is the authoritative integration artifact.
- The existing `contentHash(record)` is a deterministic eight-hex change detector over the authored record plus card projection. It is suitable as the current record precondition because the server already exposes it, but it is not a cryptographic identity and must remain distinct from the SHA-256 canonical request fingerprint.
- Replay lookup must precede `requireRecord`: a proposal that was committed while a record was active must still be recoverable after a later bundle withdraws that record. Only a genuinely new event evaluates active-record and content-hash preconditions.
- Current upstream regression surfaces are split across `findings.test.ts`, `proposals.test.ts`, `tools.test.ts`, and the built-process acceptance script. Phase 19 needs both unit-level store race/durability cases and stdio-level schema/annotation/lookup proof; changing only a helper test would not prove the shipped bundle.
- Frontier Isles already validates `idempotencyKey` as `frontier-isles:` plus a stable 18..240-character routing key. Phase 19 should map that value directly to upstream `client_event_id`; adding another caller identity would create two deduplication authorities.
- Canonical request fingerprints should use the existing provenance convention `sha256:<64 lowercase hex>`. The xFrontier `expected_content_hash` remains a separate 8-lowercase-hex atlas change detector.
- Compatibility must be asymmetric: v1 envelopes remain inspectable, but cannot be silently upgraded into strong writes because they never froze a record content hash. New record proposals require a v2 envelope; 0.5 stays readable but cannot receive delivery.
- The existing SQLite receipt table is terminal-per-attempt (`attempt_id UNIQUE`) and its outbox state enum deliberately has no retryable value. Receipt reconciliation therefore needs its own append-only table rather than overloading an old attempt or rebuilding the state CHECK constraint.
- A safe retry remains visibly `uncertain`; an authoritative `not_found` reconciliation is the capability that permits leasing the same immutable envelope again. This keeps “we once did not know” in history instead of erasing it with a new state label.
- Proposal decision import must eventually bind 0.6 records by paired `client_event_id` + `request_hash` as well as the server record ID; relying only on the legacy short remote ID recreates the ambiguity the protocol upgrade is removing.
- The local storage implementation now keeps reconciliation observations in a dedicated append-only table. `found` can close a pending/uncertain item without inventing another writer attempt; `not_found` leaves the historical state uncertain but gates an exact second lease by client event ID and request hash.
- The first storage gate is green: `apps/server/test/feedback-store.test.ts` passes 15/15, including exact not-found retry and found-without-retry closure; server TypeScript also passes at this checkpoint.
- Reconciliation ordering is insertion-authoritative (`seq AUTOINCREMENT`), not caller timestamp ordering. The timestamp remains evidence, while retry authorization always reads the most recently appended observation even if clocks tie or arrive out of order.
- Parallel implementation is now materially underway on both sides: xFrontier has isolated changes across its MCP store/tool/dispatch path plus a new store-idempotency test, while Frontier Isles retains the Phase 18 untracked data-contract files and is upgrading them in place. No real ledger JSON is modified.
- The v2 pure contract is now green (12/12 targeted, 58/58 data package): it freezes the cross-repo hash fixture, maps the existing local key directly to `client_event_id`, requires record hashes for proposals, and accepts mixed legacy/0.6 read records only when `client_event_id` and `request_hash` appear as a valid pair.
- Cross-repo canonical hashing has been directly compared with identical strong annotation arguments: both implementations produce `sha256:a2eccdb8bec677375b79ab8d77ffbeba4677ddeb1bd1bff0852f3f43bbe2b07d`. Different documented fixtures legitimately have different hashes; the algorithm and exact root shape `{tool_name, arguments}` agree.
- The server bridge now has a fail-closed split: 0.5 remains pull-only, 0.6 delivery requires a v2 strong intent before leasing; exact lookup can close an uncertain item without a writer, while `not_found` only enables a separately authorized same-request retry. The first combined client/bridge/store gate is green at 36/36 with server TypeScript passing.
- After adding the CLI recovery surface and docs, the full server suite is green at 139/139 across 11 files; server TypeScript and repository `git diff --check` also pass. CLI terminology now says `--confirm-upstream-write`: idempotency changes recovery safety, not mutation authority.

This was a command-path issue, not a code failure.
- Strong ACK/lookup parsing now has an explicit dataset-movement regression: lookup may be served by a newer current corpus while the immutable record and receipt must still match the original intent target. The targeted client/bridge/CLI/store gate is green at 39/39.
- The upstream checkout is currently clean at `fd39f37` with `main...origin/main`; it has its own `.codegraph/`, active planning files, ledger rules, and explicit MCP-specific gates. Phase 19 must preserve this clean-repository truth separately from Frontier Isles' large uncommitted worktree.
- xFrontier's `AGENTS.md` makes `ledger/` committed and append-only: MCP writes may append findings/proposals, but acceptance remains a human-only CLI operation and never edits `audit/`. Any protocol test must use an isolated store rather than the real ledger.
- The current writer seam is narrow: tool specs in `src/mcp/tools.ts` call `appendFinding` or the proposal appenders, which stamp the current `DATASET_VERSION`, generate a random id, and delegate persistence to `src/mcp/store.ts`. This supports a backwards-compatible conditional/idempotent layer without sharing Frontier Isles' database.
- The corpus already exposes `contentHash(record)` and exact dataset version inside the MCP process. Expected dataset and record hash can therefore be checked at the same synchronous tool-dispatch boundary immediately before the append, rather than trusted from a prior client read.
- The minimum protocol remains append-only: persist `client_event_id` and a canonical request fingerprint on the resulting finding/proposal, return the existing record on exact replay, and hard-fail if the same client id is reused with different content. Exact lookup can then recover an ambiguous timeout without manufacturing another ledger record.
- `XF_LEDGER_DIR` is the supported isolation seam and all protocol tests must use it. The repository gate distinguishes new files from grandfathered history and forbids modifying/deleting/renaming existing JSON records, so upgrading old records in place is not an option.
- A client id is routing/deduplication metadata, not identity or trust: `by_type` must remain server-stamped `model`, and the self-reported `by`/`filed_by` semantics must not change. Human accept/reject stays outside MCP.
- Required upstream gates are proportional and explicit: `npm run check` plus `npm test` for TypeScript, and `npm run test:mcp` after rebuilding the baked `dist-mcp/server.mjs`; the real ledger must remain unchanged throughout tests.
- Current persistence is `writeFileSync(..., {flag:'wx'})` directly to the final JSON path. It avoids overwrite/interleaving but is not crash-durable: a torn/partial final file is possible and there is no file or directory fsync. The protocol upgrade should write a same-directory exclusive temp, fsync it, rename to the immutable final name, then fsync the directory.
- All three write schemas currently reject additional properties and advertise `idempotentHint:false`; adding optional conditional/idempotency fields is therefore wire-compatible only after the server version changes. The `initialize` instructions also incorrectly mention only two `propose_*` writers even though `report_finding` writes.
- Proposal tools already call `requireRecord` and have the resolved `RawRecord`, so `expected_content_hash` can be checked cheaply against `contentHash(record)`. Record-scoped findings allow withdrawn/unknown ids and therefore need a narrower rule: only an active record target may carry/require a record content hash; field/population findings cannot truthfully bind one record hash.
- Upstream responses already return the complete stored record under `filed`/`queued`. Adding `client_event_id`, a canonical `request_hash`, and an `idempotent_replay` boolean preserves the existing receipt shape while making a replay observable; exact lookup should return the same record without appending.

## Technical Decisions
| Decision | Rationale |
|----------|-----------|
| Use one coherent product loop as the planning unit | It prevents the atlas, island, comparison, model, and notebook from becoming disconnected feature panels |
| Put E2E harness stabilization and entry-bundle headroom in the enabling tranche | Both affect the safety of every later visible change |
| Make learner-authored models the recommended product tranche | It converts the existing two-family demonstrator into a learner-owned scientific workflow |
| Keep AI outputs inspectable and non-authoritative | This preserves the append-only-ledger and human-ratification invariants |
| Extend the model subsystem through a versioned declarative spec before adding new kernels | The current two hard-coded runtime branches cannot safely support learner authorship or inspectable AI scaffolding at scale |
| Keep generated model specs local until an explicit human publish/review contract exists | A learner model receipt is personal exploration material and cannot silently become a ledger claim or graph edge |
| Start with a bounded declarative rule vocabulary, not arbitrary JavaScript or formula evaluation | It can express the two existing families while remaining deterministic, browser-safe, testable, and accessible |
| Add authoring code only behind the existing lazy model boundary | The eager-entry denylist and remaining bundle headroom make a new boot-path runtime unacceptable |
| Replace suggestion-only AI with bounded autonomous investigation | It matches the current night-shift architecture and makes AI a worker in the scientific loop rather than a text-completion feature |
| Separate execution authority from epistemic authority | AI may plan, run, iterate, and record; promotion into shared claims, mappings, publication, or governance follows explicit capabilities and review |
| Select bounded autonomy over suggestion-only or unrestricted sovereignty | It is the only option that is both genuinely AI Native and compatible with the current ledger/capability architecture |
| Make `MissionContractV1` the unit of authorization | One scoped authorization can cover many reversible steps while budgets, stop conditions, resources, and effects remain enforceable |
| Target A2 investigation before multi-agent execution | The current scout proves narrow resident autonomy; the next unknown is plan/run/evaluate/revise behavior within one inspectable mission |
| Keep mission contracts and runner on explicit core subpaths | This creates one shared policy layer without pulling new runtime values into the eager web barrel |
| Adapt rather than rewrite `runNightShift` | Its injected IO boundary already supports metering and preserves established behavior and tests |
| Meter before each network/write call | A depleted budget prevents the next effect instead of merely recording an overrun afterward |
| Keep the MCP capability gateway authoritative beneath mission policy | Mission authorization and existing actor capability checks are additive safety layers, not substitutes |
| Stop after the runtime/scout proof before adding UI or providers | The next unknown should be A2 scientific behavior; provider and interface complexity would obscure whether the mission semantics themselves work |
| Repair scope matching and pre-effect control polling before adding persistence | These are authorization invariants, and durable recovery must not preserve or replay a decision made under a leaked scope or stale control state |
| Persist a two-state `running` / `settled` envelope atomically | A surviving `running` marker turns an ambiguous crash into a safe stop; a settled paused bundle may be resumed, while terminal bundles are reused without repeating effects |
| Treat the checkpoint digest as content addressing, not authentication | SHA-256 detects accidental or untracked mutation relative to the record, but it does not replace signatures or filesystem permissions against an adversary who can rewrite both payload and digest |
| Retry E0/E1 automatically, but stop on uncertain E2/E3 failures | Reversible reads/computation may repeat; a shared or production write cannot be replayed safely unless its destination independently proves idempotency |
| Share one pure model runtime between manual and autonomous paths | A separate agent-only simulator would let the UI and mission produce divergent observations from nominally identical parameters |
| Keep the first A2 investigator deterministic and provider-free | It proves authorization, plan/evaluate/revise semantics, budgets, failed predictions, and replay before provider variability or UI complexity is introduced |
| Give the notebook its own hand-parsed mission projection | `explorationNotebook` loads eagerly and `guardEntryChunk` denylists `zod`, so borrowing only the receipt's types makes the boundary a build error rather than a review convention |
| Re-assert epistemic status at the storage parse boundary | Persisted JSON is the one surface where a record could gain authority nobody granted it; a stored `ledgerEffect` other than `none` is refused instead of trusted |
| Persist evidence, never resume authority | Dropping the contract, event log, and step inputs means a notebook record can be read and re-checked but cannot restart or extend a mission |
| Discard an internally inconsistent record rather than repairing it | A summary that claims more failures or runs than its surviving trials can show would misreport the investigation; showing nothing is the honest failure mode |
| Treat the "current page session only" line as code, not copy | Persisting the record made that reassurance false, so it had to change in the same commit that made it false |
| Snapshot module-loaded xfrontier references and surface withdrawals | This detects additions/removals locally, preserves active content hashes for later live comparison, and prevents a retired source from masquerading as current provenance |

## Plan Arbitration

| Candidate | Result | Reason |
